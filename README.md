# AIS3 CTF step-extraction scoring pipeline

## Project website

The public research showcase lives in [`site/`](site/). It presents the
step-level evaluation method, aggregate results, a representative interactive
challenge explorer, limitations, and project acknowledgements.

Preview it locally without a build step:

```bash
python3 -m http.server 4173 --directory site
```

Then open `http://localhost:4173`. The root `vercel.json` maps the deployed
site to this directory.

Scores LLM agent CTF solve transcripts against official reference writeups,
using a shared `ctf-step` JSON schema for both. Two independent signals:

- **Anchor matching** (decisive): does the agent's own text contain the
  literal tokens (`anchors[]`) a ground-truth step requires? This is the only
  signal that decides whether a step counts as "reached."
- **Milestone-embedding similarity** (exploratory, local, Qwen3-Embedding-0.6B):
  did the agent's own step milestones look semantically close to a
  ground-truth step? Shown for context only, never used to decide reached-ness
  — a model can describe the right idea while being on a completely wrong
  path.

See the module docstrings in `src/score_steps.py` and `src/anchor_match.py`
for the exact matching rules, and `src/METHODOLOGY.md` for a short summary.

## Data layout

```text
Dataset/
  README.md / INDEX.md / PROMPT.md   # dataset provenance + extraction spec
  json/<challenge>/reference.json
  json/<challenge>/agent/<solver>/run-XX.json
  writeups/<challenge>/reference.md
  writeups/<challenge>/agent/<solver>.md
```

`<challenge>` is the Dataset folder name (e.g. `C01_crypto_ROT13`) — the
`C`/`R`/`D` prefix means Contaminated/Recent/Deep (data-provenance grouping,
independent of topic). This is the canonical challenge id used by
`score_steps.py`/`render_table.py`; the JSON's own internal `"challenge"`
field (e.g. `crypto_picoctf5`) predates this layout and is kept only as
`challenge_slug` metadata.

## Setup

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

`requirements.txt` currently pins the **CPU-only** torch wheel
(`torch==2.13.0+cpu`). The embedding pass (Qwen3-Embedding-0.6B, ~942 agent
runs) is noticeably slow on CPU. To run on GPU instead, install a
CUDA-enabled torch build matching your driver/GPU before installing the rest
of `requirements.txt` — `sentence-transformers` picks up CUDA automatically
if `torch.cuda.is_available()`.

## Running

```bash
python3 src/score_steps.py                 # score all challenges (anchors + semantic)
python3 src/score_steps.py --no-semantic    # anchor-only, much faster
python3 src/score_steps.py --challenge C01_crypto_ROT13
python3 src/render_table.py                 # -> output/step_scores_table.html
```

`output/` is git-ignored (regenerated by the two commands above).

## Viewing results

`output/step_scores_table.html` is a single self-contained file (CSS/JS/icons
all inlined, no CDN or network calls) — no server needed, just open it
directly in a browser.

**Note: clicking the file on github.com only shows the raw HTML source, not
the rendered report** — GitHub's file viewer doesn't execute HTML/JS. To
actually see the report:

1. `git clone git@github.com:YuCheng1122/ais-final.git` (or `git pull` if
   already cloned)
2. Open `output/step_scores_table.html` locally — double-click it in your
   file browser, or drag it into a browser tab, or `open`/`xdg-open
   output/step_scores_table.html`

(Alternative without cloning: on the file's GitHub page, click **Raw**, then
save that page as `.html` and open it locally the same way.)

`python3 -m http.server` from `output/` also works if you want to share it
over a local network instead.

- **Sidebar**: `Overview` (cross-challenge leaderboard) + one button per
  challenge, filterable by the search box.
- **Overview page**: per-model solved/total, broken down by challenge
  category and by data source (Contaminated/Recent/Deep). "Solved" means at
  least one run's `flag_status` was `retrieved`. Click a model name to expand
  its challenge list and two fail-rate matrices (by `result_type` and by
  `interaction_mode`, green→red = low→high failure) — useful for spotting
  what kind of step a model tends to fail at.
- **Per-challenge page**: top table is a per-model summary (best stage
  reached, flag retrieval rate, which steps are still a gap below the best
  run). Below it, one row per ground-truth step × one column per model, cell
  = `N/n_runs` reached.
- **`N/n` badge = the only "reached" signal**, decided purely by literal
  anchor matching. Click it to open the detail panel at the bottom of the
  screen: which of the agent's own steps carried the matching anchor text
  (highlighted), plus that run's top semantic (embedding) matches shown as
  extra context — semantic score is *never* what decides reached-ness, only
  anchors are.
- The purple **flag badge** (`flag_status`) is a separate signal from the
  anchor "reached" badges — a step can be reached without the flag being
  retrieved, and vice versa. Don't conflate the two.
- The report is a snapshot of `output/step_scores/*.json` at render time —
  re-run `render_table.py` after re-scoring to refresh it.
